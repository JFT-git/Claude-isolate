# Claude Isolate

[![CI](https://github.com/JFT-git/Claude-isolate/actions/workflows/ci.yml/badge.svg)](https://github.com/JFT-git/Claude-isolate/actions/workflows/ci.yml)

Экспериментальная изолированная Linux-среда для Claude Desktop и Firefox.
QEMU запускает отдельную ОС без общих папок, буфера обмена, камеры, микрофона,
проброса USB и входящих портов. Сетевой шлюз использует системный маршрут хоста:
подходит системный VPN, который направляет **весь трафик шлюза** через туннель.
FlClash не требуется. Это не VPN-клиент и не гарантия отсутствия блокировок аккаунта.

VPN с Fake-IP DNS может возвращать виртуальные адреса `198.18.0.0/15` вместо
адресов сайтов. Начиная с Windows v0.3.4, шлюз разрешает такие имена через
проверенное HTTPS-соединение с Cloudflare DNS, используя тот же системный маршрут.
К виртуальным адресам он не подключается. Реальные локальные адреса, смешанные
публичные/непубличные ответы и недоступность защищённого DNS по-прежнему закрывают
доступ. При ошибке запуска окно и `launcher.log` показывают домен и причину.
Включайте TUN/полный туннель: системный HTTP-прокси сам по себе не перенаправляет
TCP-соединения этого шлюза. После обновления контроллера диск Linux пересоздавать
не требуется. [Fake-IP DNS](https://github.com/MetaCubeX/Meta-Docs/blob/main/docs/config/dns/index.md),
[Cloudflare DoH](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/make-api-requests/dns-json/).

В v0.3.4 также исправлена ошибка файлового обмена Windows: чтение сетевого
статуса больше не блокирует его атомарное обновление. При временной ошибке записи
проверяющий поток закрывает сеть отдельным маркером и продолжает проверки,
вместо завершения с `PermissionError / WinError 5`. Только новая успешная проверка
может снять временную паузу; смена IP по-прежнему требует перезапуска среды.

## Платформы и загрузка

| Платформа | Артефакт CI | Состояние |
| --- | --- | --- |
| macOS 14+, Apple Silicon | `Claude-isolate-macos-arm64.zip`, нативный `.app` | Локально проверен запуск VM, Claude и Firefox |
| macOS 14+, Intel | `Claude-isolate-macos-x86_64.zip`, нативный `.app` | Сборка и тесты в CI; запуск VM на Intel ещё не проверен |
| Linux x86_64 / ARM64 | `Claude-isolate-linux-*.zip`, исходники и CLI | Экспериментально; отдельного графического контроллера нет |
| Windows 10 1903+ / 11 x64 | `Claude-isolate-windows-x64-setup.exe` или `Claude-isolate-windows-x64.zip` | Окно управления и фоновый `.exe`; установка, запуск GUI и шлюз проверяются на Windows в CI |

Готовые артефакты находятся в **Actions → CI and release → Artifacts**.
По тегу `v*` после успешных тестов и SAST/SCA создаётся предварительный GitHub Release.
Сборка сама по себе не подтверждает работу изоляции на реальном компьютере.
Приложение Claude, Ubuntu, QEMU и диски с аккаунтами в архивы не включаются.

## macOS

Установите `.app` в `/Applications` или `~/Applications`, включите системный VPN
и запустите приложение. Кнопки позволяют запустить, остановить и перезапустить среду.
Homebrew, Python 3.12, QEMU и GnuPG устанавливаются при необходимости.
Homebrew.pkg проверяется средствами macOS; при его установке возможен системный
запрос пароля администратора. Затем загружается Ubuntu 24.04, проверяются подпись
закреплённого ключа Ubuntu и SHA256, создаётся отдельный диск до 64 ГБ.
По умолчанию используется экономный режим: **3 ГБ RAM и 2 CPU**.
В контроллере можно выбрать стандартный режим **6 ГБ / 4 CPU**, предварительно
остановив среду. Старые настройки ресурсов сохраняются до выбора нового режима.
Для хоста разумно иметь не менее 8 ГБ RAM; множество вкладок и тяжёлые проекты
потребуют больше памяти. 64 ГБ — предельный размер разреженного диска, а не
место, занимаемое сразу. Лёгкий XFCE устанавливается без набора лишних драйверов,
композитор отключён, установочный кэш очищается и свободные блоки возвращаются
хосту через TRIM. Образ Ubuntu после успешной подготовки удаляется.

Новая среда хранится в `~/Library/Application Support/Claude Environment`,
поэтому приложение можно установить в Applications. Если рядом с `.app` уже есть
**Claude Environment Data/environment.json**, продолжает использоваться эта
папка. Не удаляйте данные: там находятся файлы гостя и сеансы входа. Перенос
существующей среды потребует обновить абсолютные пути в `environment.json`.
Не держите рабочую установку в Documents/Desktop/Downloads: фоновые дочерние
процессы могут вызывать запросы macOS на доступ к защищённой папке. При отказе
автоматические проверки приостанавливаются до явного повторного действия.

Сборки имеют локальную ad-hoc подпись, **без Apple Developer ID и notarization**.
Gatekeeper может потребовать разрешение на открытие в настройках macOS.
Проверяйте источник и SHA256; отключать системную защиту целиком не нужно.
Чистая установка без Homebrew и работа Intel VM требуют отдельного ручного теста.

Рабочий стол, Claude, Firefox, русский/английский язык устанавливаются автоматически.
Переключение: **Alt+Shift / Option+Shift** или индикатор на панели.
Гость использует 1920×1200, XFCE 144 DPI, Claude 150%.
Гостевое окно Mac открывается на весь экран; выход — меню View → Enter Fullscreen.
Вход в аккаунт и принятие условий Firefox выполняет пользователь.

Сборка из исходников:

```sh
python3 macos/build.py --arch arm64
# Intel:
python3 macos/build.py --arch x86_64
```

Результат: `dist/Claude Environment.app`. Нужны инструменты разработчика Apple.

## Linux CLI (экспериментально)

Для Ubuntu/Debian x86_64 установите зависимости:

```sh
sudo apt-get update
sudo apt-get install python3 qemu-system-x86 qemu-utils genisoimage gnupg
```

Для ARM64 вместо `qemu-system-x86` нужны `qemu-system-arm qemu-efi-aarch64`.
Нужны графическая сессия и доступ пользователя к `/dev/kvm`.
Запуск из распакованного каталога:

```sh
sh packaging/start-linux.sh
```

При первом запуске создаётся `environment.json`, загружается подписанный образ
Ubuntu подходящей архитектуры и готовится диск. Гость установит приложения сам.
Для нестандартного пути данных используйте явные команды:

```sh
python3 scripts/configure.py --data /absolute/path/to/private-vm
python3 scripts/prepare.py
python3 environment.py start
```

Если диск уже существует, подготовка откажется его перезаписывать.
На Linux/Windows пока нет подписки на сетевые события, аналогичной Darwin
`AF_ROUTE`: используется периодическая проверка внешнего IP. Проверка каждые
2 секунды и срок разрешения 6 секунд **не означают мгновенную защиту от утечки**.
Не используйте экспериментальные порты там, где критична мгновенная блокировка.

## Windows

Скачайте **`Claude-isolate-windows-x64-setup.exe`** из Releases и установите
приложение. Оно появится в меню «Пуск». Установщик приложения работает для текущего
пользователя; Python уже включён. Для переносимого варианта распакуйте ZIP целиком
и откройте **`Claude Isolate.exe`**. Рядом должны оставаться `Claude Isolate Core.exe`
и папка `_internal` — это одна установка.

В окне есть кнопки запуска, остановки и перезапуска среды, выбор ресурсов и доступ
к журналам. Windows v0.3.12 содержит Python, проверенный QEMU x64 с необходимыми
библиотеками и отдельный GnuPG. Winget, Microsoft Store, установка WSL/Hyper-V,
ручное включение компонентов Windows и права администратора не требуются.
Для ZIP сохраняйте рядом с exe папки `_internal` и `runtime`.
Ubuntu загружается автоматически с проверкой подписи и SHA256. Создание ISO
выполняется встроенной библиотекой. Linux сам устанавливает рабочий стол,
Claude Desktop, Firefox и раскладки.

Данные находятся в `%LOCALAPPDATA%\Claude Isolate`. Удаление контроллера их
сохраняет. Уже доступное аппаратное ускорение WHPX используется автоматически;
иначе приложение запускает программную эмуляцию. Она медленнее, особенно при
первой установке. Настройки компонентов и безопасности Windows не меняются.
Автоматический профиль выделяет **2–3 ГБ RAM и до 2 CPU**, оставляя резерв
памяти Windows. Рекомендуется ПК с **8 ГБ RAM**; при недостатке свободной памяти
приложение предлагает закрыть другие программы. Поддерживается Windows 10
1903+ / 11 x64; Windows 7 и 32-битные системы не поддерживаются.
В Windows v0.3.5 появился выбор режима запуска. В автоматическом режиме,
если QEMU аварийно завершился через WHPX в первые три минуты, приложение
один раз повторяет запуск через TCG и запоминает его для этого компьютера.
Предыдущий процесс и шлюз перед повтором закрываются, диск сохраняется,
сеть проверяется заново и должна иметь тот же выходной IP. Ошибка проверки
сети не вызывает повторного запуска. Для повторной попытки WHPX заново
выберите «Автоматически» или «Аппаратный: WHPX»; для проблемных компьютеров
доступен постоянный «Совместимый: без гипервизора». Более позднее падение
не вызывает автоматического перезапуска работающей среды.
В v0.3.6 контроллер сам подключается к QMP и сохраняет соединение до остановки:
Windows QEMU ждёт этого подключения перед загрузкой и допускает только одного
клиента. Команды остановки и проверки передаются владельцу соединения через
локальные файлы с идентификатором текущего запуска; другие QMP-команды запрещены.
CI теперь ждёт появления загрузочного журнала **до** внешней проверки управления,
чтобы тест не мог случайно разблокировать зависший QEMU.
В v0.3.8 канал управления постоянно читает фоновые события QEMU, а оба
Windows-канала используют асинхронный Win32 I/O (`FILE_FLAG_OVERLAPPED`) с
отдельными событиями завершения для чтения и записи. Это устраняет взаимную
блокировку синхронного Windows I/O и задержки SSH до следующего keepalive.
CI проверяет настоящий Windows named pipe с одновременно ожидающим читателем
и большой записью, затем скачивает через собранный шлюз пакет
GnuPG размером более 7 МБ и проверяет его закреплённый SHA256.
В v0.3.9 шлюз автоматически выбирает совместимый файловый адаптер в Wine /
CrossOver. На настоящей Windows остаётся проверенный асинхронный Win32 I/O.
Это позволяет повторять проверку Windows EXE на Mac; аппаратный WHPX в Wine
недоступен, поэтому там нужен совместимый режим TCG.
В v0.3.10 записи в канал ограничены 2048 байтами, чтобы не передавать
крупные фреймы фиксированному буферу Windows-драйвера QEMU. SSH повторяет
частичные записи без потери данных. При EOF канала дочерний ретранслятор
всегда завершается и возвращает слот соединения.
В Windows v0.3.12 окно QEMU использует GTK без OpenGL и виртуальный USB-планшет:
абсолютные координаты подходят для RDP и не требуют захвата и перемещения мыши
в относительном режиме SDL. Проверка CI обращается к QMP после запуска рабочего
стола и проверяет активное абсолютное устройство ввода. Явно выбранный `sdl`
сохраняет виртуальную USB-мышь, чтобы избежать зависания переключения режима SDL.
Windows-сборка также содержит проверяемый набор корневых сертификатов Mozilla:
первый запуск не зависит от предварительного обновления корней через Schannel.
Проверка сертификатов и имени HTTPS-сервера остаётся обязательной.
Сетевой шлюз устанавливается как постоянная служба Linux и запускается при
каждой загрузке независимо от cloud-init. При обновлении старого образа,
который ещё не содержит этой службы, приложение автоматически создаёт
отдельный исправленный образ. Старые диск, ISO и настройки сохраняются;
вход в аккаунт в новой среде выполняется заново.
В v0.3.11 отдельная постоянная служба подтверждает запуск графической сессии
через Xrandr и сообщает готовность при каждой загрузке. Статус больше не зависит
от того, вывел ли systemd сообщение о запуске LightDM в загрузочную консоль.
Гостевое окно открывается отдельно; **Ctrl+Alt+F** включает полный экран.
Новая Windows-среда по умолчанию подбирает ресурсы автоматически. Существующие ручные настройки сохраняются.

Контроллер владеет деревом процессов через Windows Job Object: при аварийном
закрытии окна QEMU и дочерние реле завершаются. Кнопки остановки и перезапуска
сначала закрывают сеть и просят Linux корректно завершить работу. Управление
QEMU идёт по локальному named pipe, без слушающего TCP-порта.
Сетевой шлюз Windows работает через отдельный virtio-serial канал с SSH
мультиплексированием. На хосте нет TCP-сервера SSH: команды, терминал и передача
файлов запрещены; каждый разрешённый канал проходит через обычный фильтр реле.

В Windows CI проверяются сборка обоих exe, открытие GUI **без Python, winget и внешнего QEMU в PATH**,
установка/удаление приложения, сохранение данных, создание ISO и завершение
дерева процессов. Отдельная временная Ubuntu VM с настоящим GTK-окном проверяет
автоматическую установку Claude, Firefox и рабочего стола, запуск графической
сессии без ручных действий, загрузку, канал
управления и работу сети после второй загрузки той же установленной системы,
параллельные HTTPS-соединения через **собранное реле** и блокировку
прямого интернета/локальных адресов. Этот тест не входит в аккаунты и не заменяет
ручную проверку полного рабочего стола на конкретном Windows/VPN/оборудовании.
Быстрая реакция на события смены маршрута Windows пока не реализована:
сохраняется периодическая проверка IP, описанная выше.

Сборка без Authenticode-подписи: проверяйте источник и опубликованный SHA256.
Локальная сборка требует Windows x64, Python 3.12, 7-Zip и Inno Setup 6.3+:

```bat
packaging\check-windows.cmd
```

Результат — установщик `dist/Claude-isolate-windows-x64-setup.exe` и portable ZIP.
Зависимости сборки закреплены версиями и хешами в `requirements-windows.txt`
и отдельно проверяются SCA.

## Сеть и границы изоляции

- QEMU: `restrict=on`, IPv6 отключён; единственный гостевой выход — шлюз
  `10.0.2.100:7890`. Гостевой nftables разрешает только шлюз, loopback и DHCP.
- `network_mode: system`, `web_access: public` позволяют публичный HTTPS:443
  и HTTP GET/HEAD:80. Локальные, служебные и непубличные IP блокируются.
  DNS разрешается один раз, проверяется и используется точный проверенный IP.
- `web_access: services` включает ограниченный список сервисов.
  Необязательный `network_mode: proxy` поддерживает локальный HTTP CONNECT proxy
  без авторизации, но только ограниченный список сервисов.
- Проверка IP идёт через тот же транспорт к Cloudflare trace (поля `ip`, `loc`);
  `colo` не используется как страна. Неизвестная страна, RU и ошибка проверки
  закрывают сеть. При смене IP блокировка остаётся до нового запуска среды.
- На Mac изменения маршрутов приостанавливают шлюз до свежей проверки.
  Проверка активных соединений каждые 20 мс — интервал контроля, а не обещание
  полного отсутствия пакетов после изменения маршрута.
- VPN с раздельной маршрутизацией может направлять разные сайты разными путями.
  Совпадение IP проверочного сервиса не доказывает маршрут каждого назначения.
- Временная ошибка проверки закрывает сеть, но после подтверждения прежнего IP
  она восстанавливается. HTTP 429 учитывает `Retry-After`.
- Гостевой пользователь без sudo; SSH, shared folders и clipboard отсутствуют.
  Chromium sandbox остаётся включён.
- Гость видит свою ОС, виртуальные устройства, свой IP и сведения аккаунта.
  Он не скрывает условия использования или географические правила сервиса.
- `--password-store=basic` убирает запрос keyring; дополнительных гарантий
  шифрования секретов в госте нет. Защищайте диск VM средствами хостовой ОС.

## CI/CD и безопасность

Каждый PR, push в main и тег запускает тесты на пяти runner-платформах.
Раз в неделю запускается повторная проверка зависимостей и кода.

- **SAST:** Bandit для Python; CodeQL для Python, Swift и GitHub Actions.
  Bandit medium/high и CodeQL security severity ≥4 блокируют релиз.
- **SCA:** pip-audit для закреплённых инструментов сборки/проверки; Trivy для
  исходников и реального дерева подписанных Debian-пакетов гостя на AMD64/ARM64.
  HIGH/CRITICAL, включая ещё не исправленные CVE, блокируют релиз.
- **Секреты:** Trivy сканирует текущие исходники. Диски VM, журналы и конфигурации
  пользователя исключены. Это не полная проверка истории Git.
- **SBOM:** CycloneDX и список точных версий гостевых пакетов сохраняются в Artifacts.
- Actions закреплены по SHA, Python-инструменты — версиями и хешами.
  Dependabot предлагает обновления еженедельно.
- По тегу, например `v0.2.0`, релиз публикуется только при успешных проверках.
  Все релизы пока помечаются prerelease; ZIP сопровождаются SHA256.

```sh
python3 -m unittest discover -s tests -v
python3 -m venv .venv
.venv/bin/pip install --require-hashes -r requirements-security.txt
.venv/bin/bandit -r environment.py network_guard.py network_transport.py route_guard.py ubuntu_image.py session_lock.py macos scripts -ll
.venv/bin/pip-audit --strict --disable-pip --no-deps -r requirements-security.txt
```

Настройте branch protection с обязательным CI, если нужно запрещать слияние
непроверенных PR; файлы workflow сами по себе не меняют настройки репозитория.
Подробные ограничения покрытия и политика исправлений — [SECURITY.md](SECURITY.md).

Документация инструментов: [GitHub runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners),
[CodeQL](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options),

## Проверка чистой установки

Опциональный интеграционный тест создаёт **новую** VM, ставит настоящий рабочий
стол, запускает Claude и Firefox без аккаунтов, проверяет прямые/проксированные
соединения, повторное применение firewall и раскладку клавиатуры. Требуются
зависимости QEMU и рабочий VPN/разрешённый выход. Путь должен отсутствовать:

```sh
python3 scripts/integration_vm.py --data /absolute/path/to/new-audit-vm
```

Результат — `result.json`, `boot.log` и `launcher.log` в тестовой папке.
Тест не отключает VPN и не меняет маршруты хоста. После успешного теста гостевая
система выключается. Этот тест запускается вручную; обычная матрица CI проверяет
ядро, сборки и безопасность, но не заменяет запуск VM на каждой платформе.
